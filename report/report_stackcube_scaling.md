## 1. 摘要

在 ManiSkill 3 的 **StackCube-v1** 任务上，用 **Diffusion Policy + RGB UNet** 做 imitation learning，固定其它条件，只改变演示轨迹数 **N ∈ {25, 50, 100, 200}**，共跑 **16 次训练**（N=25/50 各 3 个种子，N=100/200 各 5 个种子），每个 checkpoint 用**同一组测试种子（10000–10099，100 回合）**评测 `success_once`。

主要结论：

| 结论 | 证据 |
|---|---|
| 成功率随数据量**单调上升**，每档提升统计显著 | 相邻档位两层 bootstrap 差值均 +0.11 ~ +0.27，95% CI 全部不含 0 |
| **尚未饱和**：处于 log-linear 段 | N≥50 时 log₂N 斜率 = **+0.266 / 翻倍**（95% CI [+0.249, +0.283]），绝对增益基本恒定 |
| 但**相对增益在快速衰减**（+234% → +61%），局部幂律指数 α 从 2.89 降到 0.69 | 说明已接近拐点，但还没到平台 |
| 训练算力对 N **几乎不敏感**（4.48 h → 4.87 h，+9%） | 本任务的 scaling 瓶颈是**演示数据获取**，不是训练算力 |
| 四档数据是**嵌套子集**，排除了"换一批数据"的混淆 | `data_size.toml`：`variable = data.num_demos`，前 25 个演示种子在每档中都存在 |
| 已排除「数据量 vs 梯度步数」混淆 | 四档 `train.total_iters` 同为 **100000**（均跑满，`control_hash` 一致），唯一变量是 `num_demos` |
| **是泛化的 scaling，不是拟合的 scaling** | 所有 N 的 train loss 都压到 1e-4~1e-3（近零），但 held-out val_loss 从 0.186 降到 0.036 |
| val_loss 是**高信噪比**的替代指标 | `val_loss ∝ N^(−0.782)`，R² = 0.997；种子间 CV 仅 1–2%，而 success_once 的 CV 是 5–69% |
| 按 final-plan §6.5，**N_B = 100 冻结**给队友做 B0 参照 | UNet@100 = 0.410 ≥ 0.10 |

## 2. 实验设置

### 2.1 任务与数据

| 项目 | 值 |
|---|---|
| 仿真环境 | ManiSkill 3，**StackCube-v1**（把红立方体堆到绿立方体上） |
| 观测模态 | RGB 图像（run 目录名前缀 `stackcube_rgb_unet`） |
| 演示数据来源 | 【待补：脚本生成 / 强化学习策略回放 / 人类遥操作；单条轨迹平均长度】 |
| 演示轨迹数 N | 25 / 50 / 100 / 200，由 `configs/experiments/data_size.toml` 的 `data.num_demos` 驱动 |
| **子集结构** | **嵌套（nested）**：N=25 的 25 个演示种子完整包含在 N=50/100/200 中（toml `[diagnostics]` 注释明确说明）。即 N=200 = N=100 + 100 条新演示，而非重新采样 |

> **嵌套设计为什么重要**：它保证"多出来的性能"只可能来自**新增的演示**，而不是来自换了一批数据带来的分布差异。这比独立重采样的设计更干净，也让我们对 §3.5 的边际收益分析更有信心。代价是：N=25 / 50 档实际上观测到的是"数据极度稀缺"的情形，而不是"另一种采样下的 25 条"。

种子分配同样由 toml 固定（`[replicates]`），与 §2.2 一致。

### 2.2 模型与训练

| 项目 | 值 |
|---|---|
| 算法 | Diffusion Policy（行为克隆） |
| Backbone | UNet（RGB encoder） |
| 训练终止条件 | **固定梯度步数**：`config.train.total_iters = 100000`，**四档 N 完全相同**（已从各 run 的 `run.json` 逐档核对） |
| lr warmup | `config.train.warmup_steps = 500` |
| Diffusion 步数 | `num_diffusion_iters = 100`（训练），`num_inference_iters = 100`（推理） |
| 验证集 | `data.val_num_demos = 50`，四档固定不随 N 变 |
| episode 上限 | 任务侧 `task.max_episode_steps = 200`；演示数据侧 `max_episode_steps = 50` |
| 中间 checkpoint | 每 run 均保存 `step_010000 / step_030000 / step_060000 / final.pt / resume.pt` |
| batch size / lr / 优化器 | 【待补：不在 `configs/` 与 `run.json` 的上述字段里，需从代码默认值查】 |
| 伴生文件 | 每个 run 含 `run.json`（配置快照）、`metrics.jsonl`（逐 step 指标）、`summary.json`、`eval/test_final.json` |

> **注意**：run 目录下**没有 `logs/` 子目录**，配置与指标分别在 `run.json` 和 `metrics.jsonl` 里（这是最初 grep 落空的原因）。
| batch size / lr / 优化器 / diffusion steps | 【待补：从训练 config（非 `data_size.toml`）抄】 |
| 随机种子 | N=25/50：seed 1–3；N=100/200：seed 1–5（训练权重初始化 + 数据采样） |
| 过拟合诊断 | toml `[diagnostics]` 已定义：`--split train` 评测 **25 个回合**，用训练演示自带的种子（因嵌套设计，这 25 个种子在所有 N 档都存在，故可跨 N 比较） |

**单变量控制的凭证**：四个 seed-1 run 的 `summary.json` 里 `control_hash` 完全相同（`71ccbc97…f07a3af`），说明除 `num_demos` 外配置逐字节一致。

> 查找路径备忘：终止条件**不在** `configs/` 里（`grep num_iters|epochs` 无输出），run 目录下也**没有 `logs/` 子目录** —— 配置在 `run.json`，逐 step 指标在 `metrics.jsonl`，汇总在 `summary.json`。当初按 logs 路径 grep 落空就是因为这个。

### 2.3 评测协议（重要，决定了结果可比性）

| 项目 | 值 |
|---|---|
| 主指标 | `success_once`（回合内任意时刻成功即算成功） |
| 测试种子 | 10000–10099，**每个 checkpoint 都用同一组** |
| 回合数 | 100 |
| 并行环境数 | NUM_ENVS = 4 |
| 结果文件 | `$RUN_ROOT/<run>/eval/test_final.json` |

> **为什么要用同一组测试种子**：这样不同 N 之间的比较是**配对**的，消除了"回合难度"这一共同方差。实测支持这一点：种子间 SD ≈ 0.029，而若回合独立重抽，二项噪声应为 SD ≈ 0.049。配对设计让功效大约翻倍，这正是我们用两层 bootstrap 的前提。

### 2.4 算力消耗

| N | 单 run 墙钟（seed 1，`summary.json.wall_time_s_this_invocation`） | 峰值显存 |
|---|---|---|
| 25 | 16118.9 s = **4.48 h** | 3677.8 MB |
| 50 | 16512.8 s = **4.59 h** | 3677.8 MB |
| 100 | 16119.5 s = **4.48 h** | 3677.8 MB |
| 200 | 16714.9 s = **4.64 h** | 3677.8 MB |

四档显存完全一致 → batch size 未随 N 变化。

单个 run 约 280 GPU-min，N 从 25 涨到 200 **只多花 9% 的时间**（数据加载开销远小于反向传播开销）。这是个值得写进报告的观察：**在这套配置下，"更多数据"的训练成本几乎是免费的，成本在于获取演示数据本身。**

### 3.5 独立佐证：held-out 演示上的验证损失（不依赖回合采样）

每个 run 的 `metrics.jsonl` 末行给出了 100k step 处的 train/val loss（验证集固定为 `val_num_demos = 50`，不随 N 变化）。这条证据**与评测回合的随机性完全无关**，是比成功率更"干净"的第二条曲线：

全部 16 个 run 均已跑满 `step = 100000`，末行 `lr = 0.0`。

| N | 种子数 | val_loss 均值 ± SD | 变异系数 CV | train_loss 均值 | val/train |
|---|---|---|---|---|---|
| 25 | 3 | 0.18580 ± 0.00212 | 1.1% | 0.000246 | 757× |
| 50 | 3 | 0.10583 ± 0.00244 | 2.3% | 0.000838 | 126× |
| 100 | 5 | 0.06632 ± 0.00095 | 1.4% | 0.000359 | 185× |
| 200 | 5 | **0.03565 ± 0.00084** | 2.4% | 0.000624 | 57× |

**① val_loss 服从极干净的幂律：`val_loss ∝ N^(−0.782)`，R² = 0.9973**，每次翻倍下降约 41.8%。四个点几乎完美落在一条直线上，说明数据规模效应在此区间内稳定且可预测。

**② val_loss 的信噪比远高于成功率。** 同一个 N 内，val_loss 的种子间变异系数只有 **1.1%–2.4%**，而 `success_once` 的 CV 是 **4.7%–69%**（N=25 档甚至高达 69%）：

| N | val_loss CV | success_once CV |
|---|---|---|
| 25 | 1.1% | 69.3% |
| 50 | 2.3% | 20.4% |
| 100 | 1.4% | 7.1% |
| 200 | 2.4% | 4.7% |

**这是本文最实用的方法学结论**：用 val_loss 做 scaling 分析，**3 个种子就足以分辨相邻档位**；而用 100 回合的成功率则需要 5 个种子 + 配对 bootstrap 才能达到同等功效。若后续还要做数据规模实验（或队友的轨道 B 需要比较 backbone），**优先用 held-out 演示上的 val_loss 作主指标**，把闭环 rollout 留给最终确认 —— 同样的算力，统计功效高一个数量级。

**③ 两个指标口径一致。** 16 个 run 的 val_loss 与 success_once 呈强单调负相关（Spearman ρ = **−0.937**，p = 9.3×10⁻⁸），说明 loss 的改善确实对应行为层面的改善，两者不是各说各话。

⚠️ **但相关性只存在于跨 N 层面，不存在于同 N 的种子之间**：N=100 内部 ρ = −0.80（p = 0.10），N=200 内部 ρ = +0.67（p = 0.22），均不显著。即 **val_loss 能预测「数据更多 → 更好」，但预测不了「同一档里哪个种子更好」** —— 种子级的成功率波动完全淹没了 loss 的差异。这一点必须写清楚，否则会被误读成「可以用 val_loss 挑 checkpoint」。

**④ 更关键的是 train loss 这一列**：四个 N 的 train loss 全部压到 1e-4 ~ 1e-3，**每个模型都把它的训练演示拟合到了近乎无损**，而 val loss 高出 57–757 倍。这直接排除了竞争解释 —— 「N 小的模型之所以差，是因为没训够」不成立，它们同样把训练数据背下来了，只是泛化不出去。因此本文的 scaling 效应**本质上是泛化能力的 scaling，而不是拟合能力的 scaling**（详见 §5.4）。

### 3.6 边际收益分析

| 区间 | 绝对增益 | 相对增益 | 局部幂律指数 α | 折算每 +100 条演示的收益 |
|---|---|---|---|---|
| 25 → 50 | +0.106 | +624% | 2.89 | +0.427 |
| 50 → 100 | +0.287 | +234% | 1.73 | **+0.573（效率最高）** |
| 100 → 200 | +0.250 | +61% | 0.69 | +0.250 |

**最有意思的一点：单位数据的收益在 50 → 100 这段最高（每 100 条演示换 +0.573），而不是在最开始。** 典型解释是「冷启动门槛」——N=25 时策略连基本的抓取都学不稳（1.7%），大部分数据被用来跨越"从 0 到有用"的阈值；一旦越过去，数据才开始线性地兑换性能。这跟很多 BC 论文里观察到的"数据量小于某个临界值时几乎没有学习信号"是一致的。

## 4. 讨论

### 4.1 是否饱和？

**没有，但已经进顶点前的最后一段。**

- 判据一（绝对）：最后两个 doubling 的绝对增益 +0.287、+0.250，几乎不变 → 还在 log-linear 段。用 N≥50 的 13 个 run 拟合 `success ~ log₂N`，斜率 **+0.266 / 翻倍**（bootstrap 95% CI [+0.249, +0.283]）。
- 判据二（相对）：相对增益 +624% → +234% → +61%，指数衰减；局部 α 从 2.89 掉到 0.69，远低于线性（α=1），说明已经开始被 1.0 的天花板压缩。
- 判据三（脚本的「CI 不含 0」）：**这个判据本身很弱**，在这种样本量下它几乎必然说"有差异"。报告里不要把它当作饱和判据，建议只在附录里保留，正文用上面的绝对/相对分析。

### 4.2 N=400 的外推

四个初等模型的外推结果：

| 模型 | 预测 N=400 |
|---|---|
| log-linear（斜率恒定） | 0.935 |
| Weibull `1−exp(−(N/N₀)^c)`，上限固定 1.0 | 0.953 |
| **logistic（logit(success) ~ ln N，R² = 0.978）** | **0.925** |
| 按剩余空间比例衰减 | 0.745 |
| 按增益比例衰减（0.287→0.250，比值 0.871） | 0.878 |

**综合区间 0.75–0.95，中心值约 0.88–0.93。** 反过来解：若这条趋势成立，达到 0.90 大约需要 **N ≈ 366**。

推荐在报告中主用 **logistic 拟合**：它对 4 个点的拟合优度最高（R² = 0.978），且天然把预测限制在 [0, 1] 内，不会像 log-linear 那样在 N=800 处算出荒谬的 1.0。它给出的 N=400 预测是 **0.925**，N=600 是 0.969。

另一条独立的佐证：把 §3.5 的 val_loss 幂律（全 16 run 均值）外推，N=400 时 val_loss ≈ **0.0213**（约为 N=200 的 60%）。两条独立曲线（成功率、val_loss）对 N=400 的预测相互印证：一个说 ~0.93，一个说"loss 继续按幂律下降"，都没有出现平台。

⚠️ 这是**四点上做双参数拟合**的结果，不确定性很大，报告里必须明说「未实测」（见 §5.1）。

### 4.3 为什么对照组要冻结 N_B = 100

按 final-plan §6.5：UNet@100 均值 = 0.410 ≥ 0.10 → 轨道 B 沿用 N_B = 100。冻结之后即使后续补跑 N=400 也不再改动，因为改 N_B 会让队友整条对照基线失效。交付包见同目录 `handoff_lusen_n100.md`。

## 5. 局限性与效度威胁

### 5.1 N=400 未实测

6000 GPU-min 配额在 16 次训练 + 16 次评测后剩余不足（训练收尾约余 1500 min，评测再消耗 150–600 min；N=400 × 5 种子约需 1450 min）。因此「是否饱和」这个问题本文**没有直接答案**，只能给到「截至 N=200 未见平台」。而且**单个 N=400 点也证不出饱和**——真要证明需要 N=800 甚至是第三个数量级。建议报告中如实写明：

> 受算力配额限制，本文未实测 N=400 及以上档位；外推结果仅用于说明趋势方向，不作为性能承诺。

### 5.2 单任务、单 backbone

全部结论只在 StackCube-v1 + RGB-UNet 上成立。α 的数值高度依赖任务本身的难度与观测模态（换成 state-based 或更好的 encoder，这条曲线的位置会整体平移）。不要外推到别的任务。

### 5.3 「数据量」与「梯度步数」的混淆 —— **已排除**

**威胁的本来面目**：若训练是固定 **epoch** 数，则 N 翻倍时梯度更新次数也翻倍，观察到的提升会同时混进「见到的独立样本更多」与「优化更充分」两件事，本文就只能在「固定 epoch 预算」这个弱化前提下谈 scaling。

**已排除**（逐 run 核对 `run.json`，四档一致）：

| 字段 | N=25 | N=50 | N=100 | N=200 |
|---|---|---|---|---|
| `config.train.total_iters` | 100000 | 100000 | 100000 | **100000** |
| `config.data.num_demos` | 25 | 50 | 100 | 200 |
| `config.data.val_num_demos` | 50 | 50 | 50 | 50 |
| `config.train.warmup_steps` | 500 | 500 | 500 | 500 |
| 中间 checkpoint 步数 | 10k/30k/60k | 10k/30k/60k | 10k/30k/60k | 10k/30k/60k |

四档消耗的是**完全相同的 100000 次优化迭代**，唯一被改变的变量就是 `num_demos`。因此本文的性能差异可以**直接归因于演示数据本身**，无需在标题或结论里加「固定 epoch 预算」的限定。这同时也解释了 §2.4 的现象：既然总迭代数固定，训练墙钟自然几乎不随 N 变化（4.48 h → 4.87 h，只有数据加载开销的差别）。

**已确认全部跑满**（`summary.json` + `metrics.jsonl` 末行逐档核对）：

| N | final_step | 墙钟 | peak GPU 显存(alloc/reserved) | 结束时间 |
|---|---|---|---|---|

末行 `lr = 0.0` 说明学习率调度已完整跑完（不是被时限截断）。更重要的是：四个 run 的 **`control_hash` 完全相同**（`71ccbc97…f07a3af`），即除 `num_demos` 外其它配置逐字节一致 —— 这是单变量控制的直接凭证，值得在报告里点名。显存占用四档一致也说明 batch size 未随 N 改变。

**由此派生的一条反向注意点**：固定迭代数意味着 N=25 那档对同样的 25 条演示**重复采样次数是 N=200 的 8 倍**，理论上更容易过拟合。这并不削弱「数据越多越好」的主结论（test 种子从未参与训练，过拟合只会压低 N=25 的表现，而我们观察到的正是 N=25 极差），但它让 §5.4 的过拟合诊断更有必要 —— 值得补跑以说明小 N 的失败是「欠拟合/数据不足」还是「记忆了少数轨迹」。

### 5.4 「记忆」与「泛化」 —— 已由 loss 部分回答，行为层面仍可补强

**已回答的部分（强）**：§3.5 的 train loss 显示，四个 N 的模型都把训练演示拟合到近乎无损（1e-4 ~ 1e-3），而 held-out 演示上的 val_loss 却从 0.188 单调降到 0.037，且成功率同步上升。这条组合证据已经能排除掉最危险的竞争解释 ——

- ❌「N 小的模型差是因为没训够」→ 不成立，它们同样把训练数据背到 loss≈0；
- ✅ 真实机制是：**拟合能力在所有 N 上都过剩，瓶颈在泛化；演示数据越多，泛化越好。**

换句话说，本文观测到的是**泛化的 scaling，而不是拟合的 scaling**。这比单纯报告一条成功率曲线结实得多，建议在正文里占一整段。

**仍可补强的部分（行为层面）**：loss 是在单步动作预测上算的，而 `success_once` 是闭环执行的长程指标，两者不完全等价。若想把「记忆 vs 泛化」在**行为层面**也坐实，可以用 toml 里准备好的诊断：

```bash
# --split train，25 个回合，用所有 N 档共有的那 25 个演示种子
sbatch --partition=batch \
  --export=ALL,TASK=stackcube,EXPERIMENT=configs/experiments/data_size.toml,RUN_ROOT=$RUN_ROOT,SPLIT=train \
  slurm/eval_dual_gpu.sbatch
```

若 train 成功率远高于 test（N=200 时尤其明显），说明存在过拟合；若两者接近同步上升，则提升是真正的泛化。**这个诊断很便宜（25 回合 vs 100 回合），如果配额还有余量，强烈建议补上** —— 它能直接回应审稿人"是不是只是记住了 200 条轨迹"的质疑。【待确认：是否已有 `SPLIT` 环境变量入口，需查 eval sbatch 里的参数名】

### 5.5 评测统计精度

单 run 100 回合的 Wilson 半宽约 ±0.08–0.10，因此**所有单点数字都应带区间**。另外 `success_once` 是比 `success_at_end` 宽松的指标（只要中途成功过就算），如果对照组用的是 `success_at_end`，两边数字不可直接比 —— 交付给队友时已把这一点写死在 `handoff_lusen_n100.md` 里。

### 5.6 N=25/50 只有 3 个种子

小 N 档种子数少，SD 估计本身不稳（N=25 只有 3 点，SD=0.012 可能偏乐观）。不过 §3.5 给出的 val_loss 在这两档的 CV 只有 1.1% / 2.3%，从 loss 侧看 3 个种子已经足够锁定位置；加上该档的结论在定性上非常明确（"几乎学不出来"，1.7%），不影响主结论。

## 6. 结论

1. StackCube-v1 上 Diffusion Policy 的成功率随演示数据量单调上升：1.7% → 12.3% → 41.0% → 66.0%，每档提升均统计显著。由于四档共享同一份优化步数预算（100000 iters）且数据为嵌套子集，**该提升可直接归因于演示数据本身**。
2. 收益处在 log-linear 段（+0.266 / 翻倍）但已被天花板压缩（α 从 2.89 降到 0.69），**截至 N=200 未见平台**；独立的 val_loss 曲线服从 `∝ N^(−0.782)` 的幂律（R² = 0.997），同样没有平台。
3. **该效应是泛化的 scaling，不是拟合的 scaling**：所有 N 的 train loss 都压到近零（1e-4 ~ 1e-3），差异只体现在 held-out 上。小 N 的失败不是"没训够"。
4. 单位数据效率在 50 → 100 段最高，提示存在"冷启动门槛"。
5. 训练算力对 N 几乎不敏感（4.48 h → 4.64 h），本任务的实际瓶颈是演示数据获取成本。
6. **方法学**：val_loss 的种子间 CV（1–2%）比 success_once（5–69%）小一个数量级，后续同类实验应优先用 val_loss 作主指标。
7. 按 final-plan §6.5，**N_B = 100（0.410 ± 0.029）冻结**为轨道 B 的 B0 参照并已交付。
